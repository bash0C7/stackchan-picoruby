# picoruby-stackchan-controller

Controller engine for StackChan: a `StackChan.controller` DSL, a BLE central that talks to the robot over dRuby, a link state machine, and the daemon and CLI that run the declared actions.

## Usage

```ruby
App = StackChan.controller do |c|
  c.hold 10_000

  c.action(:face) do |s, a|
    s.face(a[0].to_sym)
    "OK face=#{a[0]}"
  end

  c.action(:chat, flags: ["no-speak"]) do |s, a|
    reply = s.chat(a.text, speak: !a.flag?("no-speak"))
    reply ? "reply=#{reply}" : "reply=(none)"
  end

  c.on_touch { |zone| puts "touch zone=#{zone}" }
  c.every(1000) { }
end
```

Each `c.action` becomes a CLI verb and a method of the controller. The block receives the `Session` and the parsed `Args` (`a[0]`, `a.int("time")`, `a.float("gain")`, `a.flag?("no-speak")`, `a.text`).

```
stackchan status
stackchan servo --yaw-left 50 --pitch-up 30 --time 500
stackchan torque on
stackchan calibrate --align-only
stackchan touch listen --count 3 --timeout 30
stackchan remote servo YL=50 PU=30 T=500
```

Built-in actions are `connect`, `status`, `stop`, `raw`, `calibrate` and `speak_audio`. `remote`, `touch` and `tui` are verbs of the CLI only.
`Link` moves `released`, `held`, `quiet`; a central that cannot connect leaves it `busy` (CLI exit 8).
The controller holds the link only while it is in use: the first action connects, `c.hold` milliseconds after the last action the link goes `quiet`, and a disconnect makes the next action reconnect.
Replies from the robot are read within 3 s; a longer wait raises `TimeoutError`, and a rejection or a robot-side exception raises `DeviceError`.
